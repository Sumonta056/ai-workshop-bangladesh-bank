00 · Start here

Claude Code, without the jargon

Claude Code is an AI coding assistant that lives in your terminal. Out of the box it can read, write and run code. Everything below is the extension layer — small pieces you add to make it understand your project.

Don't try to learn all of it today. Here is the one-line mental model for each piece — the rest of the tabs just expand on these.

  • .claude/ folder — the one place all your custom settings live.
  • CLAUDE.md — notes Claude reads every time, so it knows your project.
  • Skills — how-to guides Claude opens only when needed.
  • Hooks — "when X happens, always run Y." Automatic, every time.
  • Agents — a helper Claude with its own fresh memory for side tasks.
  • Plugins — a bundle of the above, so a whole team installs it in one go.
  • MCP — the cable that connects Claude to outside tools (DB, ClickUp, GitHub…).
REMEMBER

CLAUDE.md & hooks run every time (deterministic). Skills & agents run when Claude decides they're useful (Claude's judgement). That single line explains most design choices.

01 · Setup

The .claude/ folder

This is the home for everything you teach Claude Code. One hidden folder in your project that holds your rules, skills, agents and config.

  • It sits at the root of your project — and is usually committed to git so the whole team shares it.
  • There's also a user-level one at ~/.claude/ for your personal settings across all projects.
  • You rarely build it by hand. Run /init inside a project and Claude creates a starter for you.

What's inside

my-app/.claude/
# lives at the root of your repo
.claude/
├── CLAUDE.md        # project memory (rules, commands)
├── settings.json    # config + hooks
├── skills/          # your custom how-to guides
│   └── pdf/SKILL.md
├── agents/          # helper sub-assistants
│   └── reviewer.md
└── commands/        # /shortcuts you type
TL;DR

One folder, checked into git, that turns generic Claude into your team's Claude.

02 · Memory

What is CLAUDE.md?

A plain markdown file Claude reads automatically at the start of every session. Think of it as the sticky note on your project that Claude never forgets.

Why is it a must?

Without it, you re-explain your stack, your commands and your rules in every single chat. With it, Claude already knows them before you type a word. It's always-on context.

  • Put always-true facts here: tech stack, build/test commands, folder layout, coding conventions.
  • Keep it short (aim under ~200 lines). Anything that's a multi-step procedure belongs in a skill, not here.
  • Generate a first draft instantly with /init.

Example

.claude/CLAUDE.md
# Project: Vortibhai API

- Stack: Java Spring Boot + MongoDB
- Run tests: ./mvnw test
- Frontend: Nuxt 3, deployed on Vercel
- Never edit files in src/legacy/
- Commit style: feat:, fix:, chore:
TL;DR

Write your project's "house rules" once. Claude reads them on every session.

03 · On-demand knowledge

What are Skills?

A skill is a folder with a SKILL.md file that teaches Claude how to do one specific task. Unlike CLAUDE.md, it loads only when it's relevant — so it doesn't waste Claude's memory.

  • Every skill has a name and a description. Claude reads the description and decides if this task needs it.
  • Great for repeated workflows: "how we write PDFs", "our PR-review checklist", "our release steps".
  • If you keep pasting the same instructions into chat → that should be a skill.

Example — a tiny PDF skill

.claude/skills/pdf/SKILL.md
---
name: pdf-helper
description: Extract text, fill forms, merge PDFs.
  Use when working with PDF files.
---

## How to merge PDFs
Use pypdf. Read each file, append pages,
write the combined output...

How Claude uses a skill

Skills are pulled in on demand — Claude opens the manual only when the job calls for it.
TL;DR

A reusable how-to guide. Loaded only when relevant, so it stays out of the way until needed.

04 · Automation

What are Hooks?

A hook is a command that runs automatically when a certain event happens. The rule: "when event B happens, always do A." No asking, no forgetting.

Skill vs Hook A skill is advice Claude chooses to follow. A hook is a rule that enforces itself — it fires every time, whether Claude wants to or not.
  • Defined in settings.json.
  • Classic use: after Claude edits a file → auto-run the formatter / linter.
  • Safety use: before a command runs → block dangerous ones (like deleting things).

Example — format code after every edit

.claude/settings.json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{ "type":"command",
        "command": "npm run format" }]
    }]
  }
}

How a hook fires

You don't trigger a hook. It just runs — invisibly, on its event.
TL;DR

Automatic "if this, then that" rules. Perfect for non-negotiables like formatting and safety.

05 · Delegation

What are Agents?

A sub-agent is a separate Claude with its own fresh memory, its own instructions and its own tools. The main Claude hands it a side job, and it reports back a short summary.

Why bother Big tasks (reading 50 files, deep research) fill up the main chat's memory with noise. A sub-agent does that mess in its own window and only returns the clean answer — keeping your main conversation focused.
  • Defined as markdown files in .claude/agents/.
  • Common example: a code-reviewer agent that reviews a change in isolation and sends back the findings.
  • You can even give grunt-work agents a cheaper, faster model to save cost.

How delegation works

Heavy work happens in a separate window. Only the result comes home.
TL;DR

A helper Claude for side tasks. Protects your main conversation from clutter.

06 · Packaging

What are Plugins?

A plugin bundles skills, hooks, agents and MCP servers into one installable package. It's the sharing layer — so a whole team gets the exact same setup with one install.

Think of it as An app store for your workflow. Skills and hooks are for you. A plugin is those same pieces packaged to travel to your teammates.
  • Installed from a marketplace (a GitHub repo, npm, or your team's own registry) — no manual file-copying.
  • Plugin skills are namespaced (e.g. /security:scan) so they never clash with your own.
  • Example: a "PR-review plugin" — everyone installs it and instantly shares the same review skill, formatting hook and reviewer agent.

One bundle → the whole team

Same building blocks, packaged so everyone gets identical Claude behaviour.
TL;DR

A shareable box of skills + hooks + agents. Build once, distribute to the whole team.

07 · Connections

What is MCP?

MCP (Model Context Protocol) is a standard way to plug Claude into outside tools — your database, GitHub, Slack, Google Calendar, ClickUp, and more.

Think of it as A USB port for AI. One standard socket — and any tool that speaks MCP can plug straight in, no custom wiring per tool.
  • Without MCP, Claude only knows your code. With it, Claude can read and act on live data from real services.
  • Each connection is an MCP server that sits between Claude and the tool.
  • Example: connect a ClickUp MCP, then ask "what are my open tasks?" and Claude pulls them live.

How Claude reaches the outside

One protocol, many tools. Claude asks the MCP server; the server talks to the real service.
TL;DR

The standard "cable" that lets Claude use real tools and live data, not just your code.
