01

What Codex is & where it lives

Set the framing before touching a terminal — people conflate the old 2021 Codex with today's agent.

Lead with one sentence: Codex is OpenAI's agentic coding system — not a chatbot you ask coding questions, but an agent that reads your repo, edits files, runs commands and tests, and proposes changes. The key idea to land is that "Codex" is an umbrella over several surfaces that share one model and one account, so work started in one place can be continued in another.

  • Runs on OpenAI's latest GPT-5.x-Codex models (GPT-5.5 generation as of mid-2026), purpose-trained for long-horizon agentic coding — selectable per session, with a reasoning-effort dial.
  • One "app server" architecture underpins the CLI, IDE extension, web, and desktop app, so long-running sessions and approvals stay consistent across clients.
  • Adoption talking point: roughly 4 million developers a week by the GPT-5.5 launch — useful for "this is mainstream now," not a feature.
🎯 One-liner to open with

"Treat Codex less like an assistant you prompt once, and more like a teammate you configure — give it the same context a new hire would need, and it gets reliably better."

03

Live demo — first task in the CLI

Keep it to a real repo with tests. The audience wants to see the loop, not a toy.

Step 1 · Install & auth

Show the install — and the auth fork that decides everything

# macOS / Linux
$ curl -fsSL https://chatgpt.com/codex/install.sh | sh
# or, with Node 22+
$ npm i -g @openai/codex

$ codex # first run prompts you to sign in
Say: the first screen asks you to sign in with a ChatGPT account or an API key — and that one choice quietly decides your models, rate limits, and bill. ChatGPT login = newest models, included in your plan. API key = better for CI, but pay-per-token.
Step 2 · Run a task

Give it a real, scoped job and narrate the plan-then-act loop

$ codex "add input validation to the signup endpoint and a test for it"
Point out: Codex explains its plan before changing anything, shows syntax-highlighted diffs in the TUI, and you approve or reject inline. Press Tab to queue a follow-up mid-run. Use codex resume to reopen an earlier thread with the same repo state.
Step 3 · Close the loop

Don't stop at the edit — make it verify

Ask it to run the tests and confirm green before you accept. This is the single habit that separates "confident but subtly wrong" output from trustworthy output. Then create a Git checkpoint so reverting is one command.

⚠️ Install gotcha to mention

There's an unrelated codex package on npm from 2012 that installs silently and does nothing. Use the scoped name @openai/codex, and note you need Node 22+. On Windows, native PowerShell works, but WSL2 is smoother.

04

Core concepts to explain

These four ideas are what make Codex predictable. Spend your explanation budget here.

Sandbox mode × approval policy

The two safety knobs that work together. Sandbox mode decides what Codex can do (where it writes, whether it reaches the network). Approval policy decides when it must stop and ask you.

SettingBehavior
read-onlyCan read the workspace; no edits without approval. Good for chat/planning.
workspace-writeDefault. Reads, edits inside the workspace, runs routine commands. Network off by default.
danger-full-accessNo restrictions. Only inside an already-isolated runner (e.g. CI container).
on-requestApproval default — works in the sandbox, asks when it needs to step outside.

The recommended local preset is --sandbox workspace-write --ask-for-approval on-request. On Mac the sandbox uses the built-in Seatbelt framework; Linux and Windows have native equivalents.

AGENTS.md — durable project context

Codex's equivalent of a project brief (analogous to CLAUDE.md). It's read before any task, so every session — yours, a teammate's, or a cloud task from a GitHub issue — starts with the same rules. Version-controlled and reviewable.

# AGENTS.md (repo root)
## Architecture
- Frontend: Nuxt + TypeScript   ·   API: Spring Boot   ·   DB: MongoDB

## Working agreements
- Run `npm run lint` and tests before opening a PR
- New endpoints need an integration test
- Ask before adding a production dependency
  • Layering: ~/.codex/AGENTS.md for personal defaults everywhere → repo-root file for team rules → nested files override per-directory. Run /init to scaffold one.
  • Keep it lean. It loads into context every turn; bloat wastes tokens and confuses results. Cap is 32 KiB.
  • Honest limit: it reduces rule violations, it doesn't guarantee them. For irreversible actions, back it with execpolicy rules and approval gates — not the file alone.

MCP & skills — context beyond the repo

When the context Codex needs lives outside the codebase (issue trackers, your calendar, internal tools), connect it via MCP servers rather than pasting live info into prompts. Skills bundle reusable workflows. Both are configured in config.toml and shared across surfaces.

Models & reasoning effort

You can switch models per session and adjust reasoning effort (low / medium / high — medium is the sensible default). Higher effort helps on hard problems but is slower and burns rate limits faster. Worth a quick live toggle so people see the tradeoff is theirs to make.

05

Live demo — cloud delegation & parallel agents

This is the "walk away and it keeps working" moment. It lands well after the hands-on CLI part.

Option A · From the terminal

Fire a cloud task without leaving the shell

$ codex cloud exec --env ENV_ID "summarize open bugs and draft fixes"
# --attempts 3 → best-of-N runs
$ codex apply TASK_ID # pull the resulting diff into your local tree
Say: the cloud task runs in an isolated OpenAI-managed container — setup phase can install deps with network, then the agent phase runs offline by default. Secrets are removed before the agent phase.
Option B · The desktop app

Show several agents on separate worktrees at once

In the app you can monitor multiple threads from one window — each on its own branch/worktree, no conflicts. Mention automations (scheduled background tasks) and goal mode (runs toward an objective for hours with check-ins). The catch worth stating: parallelism only pays off with clear per-task scope — define what each agent produces and where, or you get competing changes.

Bonus · exec for CI

One line that shows Codex as automation, not just a chat

$ codex exec "write a CHANGELOG entry for commits since v2.4.0 and append it"
Say: codex exec is the non-interactive mode — streams to stdout/JSONL, exits non-zero on failure, so you can wire it into pipelines.
06

Best practices & gotchas

The "save yourself a week" slide. Frame these as lessons, not warnings.

✅ Configure the environment early

Most "bad output" is really bad setup — wrong working dir, missing write access, wrong model default. Fix AGENTS.md + config.toml first.

✅ Always verify before accepting

Make it run tests and checks. Codex produces confident output that's sometimes subtly wrong, especially in less-common frameworks.

✅ Start tight, loosen later

Begin with default permissions. Only widen sandbox/approval for trusted repos once the need is concrete.

✅ Scope parallel agents

Give each agent a clear deliverable and output location. Unscoped parallel runs produce conflicting changes.

⚠️ Git checkpoints

It can modify your codebase — commit before/after tasks so a revert is trivial.

⚠️ Teach it from mistakes

When Codex repeats an error, ask for a retrospective and fold it into AGENTS.md.

🚫 Don't demo this casually

--yolo / danger-full-access bypasses approvals and sandboxing. There are real reports of agents running destructive commands. Only ever inside a throwaway isolated runner — and say so out loud if you show it at all.

⚠️ Honest caveat for credibility

OpenAI's own README still calls the CLI experimental and under active development. It moves fast with rough edges — plan for breaking changes between versions. Saying this earns trust with a developer crowd.

07

When to reach for Codex (and when not)

Close with judgment, not hype. Developers respect a tool pitch that names its limits.

Great fit

Well-scoped, repeatable work; large refactors and migrations; running several tasks in parallel; issue-to-PR and automated review; UI/app tasks with no API (computer use); long-horizon jobs you delegate and check on later.

Be careful

Anything irreversible or high-stakes (prod deploys, DB ops, credential rotation) — gate with approvals and execpolicy. Unfamiliar frameworks where it has less training signal — verify harder. Tasks you can't clearly describe — scope first.

💬 Closing line

"The question for our team isn't whether to use Codex — it's where in our workflow cloud-delegated agent work actually pays off. Let's pick one repo this week and try it."
