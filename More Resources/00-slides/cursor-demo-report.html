01

What Cursor is now

Frame it before opening the app — most people still picture "VS Code with autocomplete."

Cursor began as a VS Code fork and still feels familiar — your extensions, themes, and keybindings carry over. But since the 2.0 / 3.0 releases it's reframed itself as an agent-first IDE: the editor is one pane among several, and the AI reasoning layer is the main event. Cursor 3.0 even ships an Agents Window (Cmd+Shift+P → Agents Window) for running many agents in parallel across repos, worktrees, the cloud, and remote SSH.

  • Codebase-aware by default. A custom embedding model indexes your repo, so the agent knows about the function three files away — not just the line you're on. This is what stops it hallucinating module paths in big codebases.
  • Model router. One subscription fronts frontier models — Claude (Sonnet / Opus), GPT-5.x, Gemini — plus Cursor's own Composer model. Switch per task.
  • Context you control. @-mentions for files/symbols, and .cursor/rules/ (the 2026 format that replaces a single .cursorrules) for glob-scoped standing conventions.
🎯 Opening line

"Cursor isn't trying to be a smarter autocomplete — it's trying to be a teammate that can read the whole codebase, drive a browser to check its own work, and run wherever you run, including your terminal."

02

Agent modes — pick the right gear

The single biggest workflow win is knowing which mode to use when. Demo this as a deliberate choice.

Ask

Plan & understand

Query the codebase, get recommendations, design an approach — read-only, makes no edits. Where you start.

Agent

Build & execute

Multi-file edits, runs terminal commands, reads errors, self-corrects across steps. The workhorse.

Debug

Find & fix

Focused on identifying and resolving errors — pairs naturally with the browser and console output.

🔁 The pattern that beats "just talk to the agent"

Plan in Ask → implement in Agent → drop to Manual edit for surgical control. Naming this loop out loud is one of the most useful things you can teach the room.

★ 03

The Browser — Cursor's superpower

This is the part to slow down on. It closes the loop between writing frontend code and seeing whether it actually works.

Cursor ships an official Browser tool (GA since 2.0) that the agent can drive — a real browser embedded in the editor. Instead of you alt-tabbing to Chrome, taking a screenshot, and pasting it back, the agent looks for itself. Invoke it with @Browser in chat, or let Agent mode reach for it automatically after a frontend change.

What the agent can actually do in the browser

🧭 Navigate & interact

Open a URL, click links, fill and submit forms, scroll — exercise real user flows.

📸 Screenshot & see

Capture the rendered page for visual analysis; falls back to coordinate-clicking when the DOM is unreliable.

🔍 Inspect the DOM

Select specific elements, read their structure, and pull page context back into chat.

🐞 Read console & network

Pull console logs and XHR/network requests to diagnose runtime errors and slow calls.

♿ Audit

Run accessibility, performance, and SEO checks (Lighthouse-style) without leaving the IDE.

🎨 Convert designs → code

Hand it a mockup; it builds toward the target and checks the result visually.

Design Mode / Visual Editor — point, tweak, then "Apply"

Toggle Design Mode (Cmd+Shift+D) and the browser becomes a DevTools-style inspector with a design sidebar. You can click any element and describe the change in plain language ("make this bigger," "swap their order," "turn this red"), or drag elements around the DOM tree and adjust spacing, colors, tokens, and layout with sliders. Multiple edits run in parallel.

The genuinely new part is the Apply step: once it looks right, you tell the agent to apply, and it finds the relevant components and writes the real code edit — using your repo's existing conventions. It moves the workflow from "screenshot + instructions" to "visually design a diff your team can review." You can also start a fresh chat with a selected element pre-attached as context, which keeps long sessions from drifting.

⚠️ Honest caveat for the room

It's powerful but not magic. Reviewers note the agent can break other states of a component, and everything depends on the repo running locally first (deps installed, env set, dev server up). Always review the applied diff across screen sizes — don't get complacent because the first glance looks right.

04

The CLI — Cursor in any terminal

The pitch: the full Cursor agent, outside the IDE — for Neovim/JetBrains users, scripts, and CI. Still in beta.

Install & first run

# macOS / Linux / WSL
$ curl https://cursor.com/install -fsS | bash
# Windows PowerShell
$ irm 'https://cursor.com/install?win32=true' | iex

$ cursor-agent # interactive session (a.k.a. `agent`)
$ agent chat "find one bug and fix it"

Headless / non-interactive — for scripts & CI

# -p / --print = non-interactive; --force applies edits without asking
$ agent -p "Add JSDoc comments to this file" # proposes only
$ agent -p --force "Refactor to modern ES6+" # actually edits

# structured output for pipelines
$ agent -p --output-format json "Analyze this CI failure and draft a Jira ticket"

# batch over files
$ find src/ -name "*.js" | while read f; do \
    agent -p --force "Add JSDoc to $f"; done

  • Shares your config. Same .cursor/rules and MCP setup as the IDE — set conventions once.
  • Push to the cloud mid-chat. Prepend & to a message to hand it to a Cloud Agent and keep going elsewhere; pick it up on web or mobile.
  • Handy commands: /model to switch, /summarize to free up context, @ to add files. Sessions are saved so you can resume.
🚫 Flag before you demo it

The CLI is beta and can read, modify, and delete files and run shell commands. --force / --yolo skips confirmation entirely — only in trusted, throwaway environments. Treat its terminal commands like a junior dev running things on your machine.

Parallel & background agents

The "I merge PRs from my phone" moment. Show the Agents Window running several at once.

Beyond a single interactive agent, Cursor runs subagents (parallel explorers, each with its own context window), background agents (cloud VM, separate branch, opens a PR when done), and full Cloud Agents (isolated VMs with terminal, browser, and desktop access, across multiple repos). Commands like /worktree isolate an agent's edits in a separate git checkout, and /best-of-n runs the same task across multiple models and lets you pick the winner.

💡 The rule that makes parallelism pay off

Give each agent a clear, narrow deliverable and its own branch/worktree. Unscoped parallel agents produce overlapping, conflicting changes — the scope-per-task is what turns chaos into throughput.

Context: rules, MCP, checkpoints

Quick but worth showing — these are what make results consistent instead of lucky.

FeatureWhat to say
.cursor/rules/Glob-scoped rule files (2026 format). Standing conventions, banned patterns, architecture notes — loaded only when relevant to the files in play.
MCPConnect external tools/data (issue trackers, browsers, internal APIs) so the agent pulls live context instead of you pasting it. Shared across IDE and CLI.
CheckpointsLocal snapshots auto-saved before significant agent changes. Click any point in the timeline to preview and restore. Separate from Git — use Git for real version control.
@-mentionsPull specific files, symbols, or past chats into context precisely, instead of hoping indexing catches them.
07

Gotchas worth flagging

⚠️ Run the app first

Browser & Design Mode need the repo running locally — deps installed, env vars set, dev server healthy. No server, no browser demo.

⚠️ Review parallel PRs

Multi-file and parallel agents can produce messy diffs. Budget human review time; don't auto-merge.

⚠️ Long sessions drift

Reasoning quality degrades in very long agent chats. Use /summarize, fresh chats, or element-scoped chats to reset.

⚠️ Index large repos

Monorepos without a .cursorignore hammer the indexer. Exclude build output and vendored code.

"The mental shift: stop driving every keystroke. Plan in Ask, let Agent build and check itself in the browser, run routine work through the CLI or background agents — and spend your attention on review and architecture."
