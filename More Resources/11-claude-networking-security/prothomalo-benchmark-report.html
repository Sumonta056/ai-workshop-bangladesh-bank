Executive Summary

The page renders fast but finishes slow. First paint lands at 380 ms and the DOM is interactive by 256 ms — excellent. But the full load event does not fire until ~4.97 s, and everything between DOMContentLoaded (561 ms) and load (4,972 ms) is third-party advertising and tracking.

Two structural problems dominate: (1) a single 3.15 MB inline state script bloats the HTML document to 4.4 MB decoded, and (2) a heavy third-party footprint — 24 external domains, 17 iframes, and 427 KB of third-party JS versus only 157 KB of first-party code.

Diagnosed Issues

Critical Warning Informational / 3rd-party

#1  3.15 MB inline state script bloats the HTML to 4.4 MB Critical

The document carries 14 inline scripts totalling 3.17 MB, of which a single blob is 3,155 KB. This is the server-rendered application state (Quintype/Bold CMS hydration data) serialized directly into the HTML. Result: decoded document size 4.4 MB for only 2,275 DOM nodes. Brotli compresses it to 407 KB on the wire, but the browser still parses, deserializes and holds 4.4 MB in memory on the main thread before hydration.
Fix: Trim the hydration payload to what above-the-fold components actually need. Move the rest behind a deferred fetch() after first paint, or stream it. Most news-feed state (related stories, section lists, ad config) does not need to be inline. Target <500 KB inline.

#2  Excessive third-party footprint — 24 domains, 427 KB JS Critical

24 distinct third-party hostnames are contacted: Google Ad Manager / DoubleClick, Funding Choices (consent), Facebook, Chartbeat, Qlitics, PushEngage, GSI one-tap, plus a chain of ad cookie-sync partners (3lift, teads, seedtag, moloco, appier, tribalfusion, onetag). Third-party JS (427 KB) is 2.7× the first-party JS (157 KB) and is the primary cause of the 4.4 s post-DCL tail.
Fix: Audit the tag stack. Load every non-essential tag with async/defer and ideally after the load event or on idle (requestIdleCallback). Consolidate analytics (GA4 + Chartbeat + Qlitics overlap). Lazy-init the Facebook pixel on first interaction.

#3  Full load gated by ads — 4.4 s between DCL and load Warning

DOMContentLoaded = 561 ms but loadEventEnd = 4,972 ms. The 4.4 s gap is entirely ad/tracker activity (GPT slot fills, sodar verification, cookie syncs, beacons). Long-running beacons like Chartbeat (4.6 s) keep the connection and main thread busy well past user-perceived readiness.
Fix: Defer ad initialization until after load or first scroll. Use GPT lazy-loading (enableLazyLoad) so below-the-fold slots only request when near the viewport.

#4  Images have no width/height and no lazy-loading Warning

All 12 above-the-fold images ship with no width/height attributes (cumulative layout shift risk) and zero use loading="lazy" — every image is fetched eagerly even when off-screen.
Fix: Add explicit width/height (or CSS aspect-ratio) to reserve layout space and kill CLS. Add loading="lazy" to all below-the-fold thumbnails; keep only the hero/LCP image eager with fetchpriority="high".

#5  17 iframes on a single page Warning

The DOM contains 17 iframes — mostly ad/safeframe containers plus the FIFA World Cup widget. Each iframe is a separate document with its own resource graph, multiplying connection and CPU cost.
Fix: Lazy-mount ad iframes (GPT lazy-load). Render the FIFA widget inline or load it on demand rather than as multiple persistent iframes.

#6  FIFA score-card iframe + API loaded 3× (redundant) Warning

services.prothomalo.com/fifawc/2026/score-card-football/ is requested as an iframe three times (4,331 ms / 1,423 ms / 1,422 ms), and the api-proxy.php?type=schedules endpoint is called three identical times (~125 ms each, ~7.9 KB each). This is duplicated work that returns the same data.
Fix: Mount the widget once and cache the schedules response (one fetch, shared across instances). This is a first-party bug fully under your control.

#7  Ad cookie-sync redirect chains Warning

A long chain of 302 cookie-matching pixels fires after load (3lift, teads, seedtag, moloco, appier, onetag, tribalfusion → doubleclick). Several take 300–570 ms each and add 15+ requests that contribute nothing to the content.
Fix: These come bundled with Google Ad Manager demand partners — partly outside your control, but you can reduce them by trimming the partner list in your GAM/consent config and deferring the ad stack until after load.

#8  Console errors: Google one-tap & FedCM Info

Runtime console shows: google.accounts.id.initialize() is called multiple times, FedCM get() rejects with NotAllowedError: Only one navigator.credentials.get request may be outstanding, Provider's accounts list is empty, and a 401 on one resource. Indicates Google GSI one-tap is being initialized more than once.
Fix: Initialize GSI exactly once. Guard the init so re-renders don't re-call it. The duplicate FedCM call is rejected by the browser and wastes a round trip.

#9  No LCP entry emitted Info

The largest-contentful-paint buffer was empty, and ad slots logged Can not detect viewport width. In a real metered field measurement LCP should be captured; its absence here suggests the largest element may be inside an iframe/ad or rendered after JS, which hurts real-world LCP attribution.
Fix: Ensure the hero image/headline is a first-party, server-rendered element with fetchpriority="high" so it becomes a clean, fast LCP candidate. Verify with field (CrUX/RUM) data.

#10  document.write from async script Info

Warning: "Failed to execute 'write' on 'Document': It isn't possible to write into a document from an asynchronously-loaded external script." A third-party (ad) script attempts document.write, which is ignored in async context and is a known performance/anti-pattern.
Fix: Identify the offending tag (typically a legacy ad creative) and replace with a DOM-injection variant; flag it with the ad partner.

#11  362 KB SVG sprite served with gzip, not Brotli Info

sprite-*.svg is the single largest non-script asset: 362 KB transfer / 573 KB decoded, served with content-encoding: gzip while the HTML uses Brotli. It is one monolithic sprite loaded up front.
Fix: Serve it with Brotli (≈15–20% smaller), and split the sprite so only icons used above the fold load initially. Ensure a long Cache-Control: immutable (the hashed filename already supports it).

Recommended Fix Order

  1. Shrink the 3.15 MB inline state blob (Issue #1). Biggest single win for parse time and memory; entirely first-party.
  2. Fix the 3× FIFA widget / schedules duplication (Issue #6). Easy, first-party, removes redundant 4.3 s iframe work.
  3. Defer the ad & tracking stack until after load (Issues #2, #3, #5, #7). Collapses the 4.4 s tail.
  4. Add image dimensions + lazy-loading (Issue #4). Cheap CLS and bandwidth win.
  5. Clean up GSI double-init and document.write warnings (Issues #8, #10). Correctness + small latency.
  6. Brotli + split the SVG sprite (Issue #11).
Methodology. Measured with a headless Chromium navigation to the live page (HTTP/2 + HTTP/3, cold cache, single pass) using the browser's own PerformanceNavigationTiming, PerformanceResourceTiming, paint and console APIs — no synthetic estimates. Numbers reflect one run from a single network vantage point; absolute timings vary with geography, device and connection. For trend tracking and regression alerts, capture a baseline (/benchmark <url> --baseline) and re-run on each release.

Third-party timings (ads, social, analytics) are reported for transparency but are largely outside the site owner's direct control; recommendations focus on first-party fixes and tag-loading strategy.
