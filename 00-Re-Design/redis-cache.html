What it is and why it exists

The backend (Spring Boot, folder vortibhai/) keeps copies of slow MongoDB read results in Redis. Redis is an in-memory key-value store. A read from Redis takes about 1 ms. A MongoDB aggregation can take 50 to 500 ms.

Single main responsibility: answer repeated public read requests (department pages, university lists, search, dropdowns) from Redis, and fall back to MongoDB when Redis has no copy or Redis is down.

The code does not call Redis directly for normal reads. It uses Spring Cache annotations: @Cacheable reads or fills the cache, @CacheEvict deletes entries after a write. The Redis setup is in config/CacheConfig.java vortibhai/src/main/java/com/admission/vortibhai/config/CacheConfig.java:27.

Analogy: Think of a library help desk. The first person who asks "list all CSE departments" makes the librarian walk to the archive (MongoDB). The librarian writes the answer on a sticky note (Redis) with an expiry time (TTL, time to live). The next 1000 people get the sticky note. When a book changes (a write), the librarian throws away the matching notes (evict).

    Step by step: one cached read request

    Example: GET /api/departments/{departmentId}/university/{universityId}.

    1. PerformanceFilter runs first for every request. It starts a timer filter/PerformanceFilter.java:45.
    2. The controller calls departmentService.getDepartmentGroupByDepartmentAndUniversity(...). The call goes to a Spring proxy, not to the real class.
    3. The proxy sees @Cacheable(value = DEPT_GROUP, key = "#departmentId + ':' + #universityId") service/impl/DepartmentServiceImpl.java:175. It builds the key, for example d123:u456.
    4. The cache manager adds the prefix from CacheConstants.prefixFor. The full Redis key is vb:v12:dept-group:d123:u456 config/CacheConstants.java:5-13.
    5. HitMissTrackingCache.get asks Redis for the key and records HIT or MISS in a ThreadLocal config/CacheConfig.java:127-132.
    6. HIT: Jackson turns the JSON back into DepartmentGroupSummaryDTO. The method body does not run. MongoDB gets no query.
    7. MISS: the method body runs the MongoDB query. The proxy then writes the result to Redis as JSON with the TTL for dept-group (15 minutes) config/CacheProperties.java:17.
    8. Redis error: ResilientCacheErrorHandler logs a WARN and the request continues as a MISS against MongoDB config/ResilientCacheErrorHandler.java:16-23.
    9. Back in PerformanceFilter, the code sets headers X-Cache and X-Response-Time, writes 1 log line, and clears the ThreadLocal filter/PerformanceFilter.java:51-63.

    Step by step: one write request

    1. An admin sends PUT /api/departments/{id}.
    2. The method runs and saves to MongoDB.
    3. After it returns, @Caching(evict = {...}) deletes the related entries: 1 exact key in dept-group, dept-sections, uni-departments, dept-by-id, plus all entries of dept-public-list, dept-facets, dept-admin-list, dept-reviews service/impl/DepartmentServiceImpl.java:816-830.
    4. The next read is a MISS and loads fresh data.

    1. Ask the real Redis cache for the key.
    2. Write HIT or MISS into a ThreadLocal (a value that belongs only to the current request thread).
    3. Only the first write counts. A cached method can call another cached method. Without this rule, an inner HIT could hide an outer MISS (comment at CacheStatusHolder.java:9-11).
    4. All other methods (put, evict, clear) pass straight through.
    4. ResilientCacheErrorHandler config/ResilientCacheErrorHandler.java:12-40 
    public void handleCacheGetError(RuntimeException exception, Cache cache, Object key) {
  LOGGER.warn("Cache GET failed [{}::{}] - serving from source: {}",

}
    • Spring calls this when Redis throws during a cache operation. It is registered at CacheConfig.java:42-45.
    • The handler does not re-throw. A failed GET becomes a MISS, so the method body runs against MongoDB.
    • A failed PUT, EVICT or CLEAR is logged and ignored. The user still gets a 200 response.
    • With the 250 ms timeouts in application.properties:109-110, a dead Redis adds at most about 250 ms per cache call.
    5. Eviction on write: @Caching(evict = ...) service/impl/DepartmentServiceImpl.java:612-626 
    @Caching(evict = {

    • #result is the value that the method returned. The key is built after the method runs, so you can only use it for evictions that run after the call (the default).
    • key = ... deletes 1 entry. allEntries = true deletes every entry in that cache. Use it for list caches, because you cannot know which pages changed.
    • This block is on POST /api/departments. The same pattern is on update (:816) and approve (:923). There are 25 @Caching blocks in the service layer.

    Scenarios that trigger this code

    Scenario A: a student opens a department page
    1. The public Nuxt app requests the department group, sections and reviews.
    2. Each call hits a @Cacheable method: dept-group, dept-sections, dept-reviews.
    3. The first visitor in 15 minutes gets MISS. Every visitor after that gets HIT until the TTL ends or an admin edits the department.
    Scenario B: an admin approves a department review
    1. The admin panel sends PATCH /api/departments/{id}/approve.
    2. The approve method saves to MongoDB, then the @Caching block at DepartmentServiceImpl.java:923 clears the department caches and the admin stats.
    3. The public page shows the new review on its next request.
    Scenario C: an admin uses the Cache page (purge or warm up)
    1. admin/pages/cache/index.vue uses useCache.ts, which calls GET, DELETE and POST .../warmup on /api/admin/cache.
    2. warmup() calls 9 public read methods (CacheAdminServiceImpl.java:98-111). Each call is a MISS and fills Redis, so the next real visitor gets a HIT.
    3. On startup, DepartmentAliasSeeder also clears search-results, dept-public-list and dept-facets if it changed data (DepartmentAliasSeeder.java:106-111).

    UI impact and events

    • Public app: no visible change. Pages load faster on a HIT. Data can be up to 1 TTL old if a write path forgets to evict.
    • Admin app: the Cache page lists each cache with key count and TTL, and has Purge, Purge all and Warm up buttons. After each action, useCache.ts invalidates the TanStack Query keys cache and stats admin/features/cache/composables/useCache.ts:16-39.
    • HTTP headers on every API response (from PerformanceFilter): X-Cache: HIT|MISS (only when a cached method ran), X-Response-Time, X-Db-Time, X-Db-Queries filter/PerformanceFilter.java:52-60.
    • HTTP calls to the backend: GET /api/admin/cache, DELETE /api/admin/cache/{name}, DELETE /api/admin/cache, POST /api/admin/cache/warmup. All need the ADMIN role CacheAdminController.java:27.
    • No messages or events: the code has no pub/sub, no scheduled job and no async task for the cache. Not found in codebase.

    How to debug

    "My change does not show on the public site"
    1. Open DevTools, Network tab. Look at the response header X-Cache. If it is HIT, you see cached data.
    2. Find the write method that you called. Check that it has a @CacheEvict for every cache that shows this data.
    3. Check that the evict key is built the same way as the @Cacheable key (same order, same ':' separators).
    4. To confirm, purge that cache on the admin Cache page and reload.
    "X-Cache is always MISS"
    1. Search the logs for Cache PUT failed. A PUT failure means nothing is stored.
    2. Check that the cache name has an entry in CacheTypeRegistry and that the method returns exactly that type.
    3. Check that the call comes from another bean. A call from the same class (this.method()) skips the proxy, so there is no cache.
    4. Run redis-cli --scan --pattern 'vb:v12:<cache-name>:*' to see the stored keys.
    "Requests are slow by about 250 ms"
    1. Search the logs for Cache GET failed. Redis is probably down or far away.
    2. Run docker compose ps redis and redis-cli ping. The compose file has a health check at docker-compose.yml:13-17.
    3. Check REDIS_HOST, REDIS_PORT, REDIS_PASSWORD in the environment.
    Breakpoints to set
    • HitMissTrackingCache.get CacheConfig.java:129: see the cache name, key and result.
    • ResilientCacheErrorHandler.handleCache*Error: see the real exception.
    • First line of the cached method body: if the debugger stops there, it was a MISS.

    Trade-offs of the current design

    ChoiceProCon
    Annotations (@Cacheable) instead of manual Redis callsLittle code; business logic stays cleanBehavior is hidden; proxy rules (self-call) are easy to forget
    Typed JSON serializer per cacheReadable values, no @class data, no unsafe polymorphic readsEvery new cache needs a CacheTypeRegistry entry; a shape change needs a namespace bump
    Error handler that never throwsRedis outage does not break the siteFailures are silent to users and easy to miss; the site gets slower, not broken
    Evict on write + TTLFresh data after writes; TTL is a safety netEach write path must list every affected cache by hand
    allEntries = true for list cachesSimple and correctOne edit clears all pages of the list; next visitors all get MISS
    250 ms Redis timeoutsFails fast when Redis is downA slow network to Redis can cause false failures
    Redis maxmemory 256mb, allkeys-lruRedis never runs out of memoryUnder memory pressure Redis drops keys before their TTL

    Gotchas for a new developer

    New cache without a CacheTypeRegistry entry high

    CacheConfig builds typed configs only for names in the registry (CacheConfig.java:50-56). Any other name gets the default config, which uses the JDK serializer. Most DTOs are not Serializable, so every PUT fails with Cache PUT failed and the cache never works. Follow the 4 steps in .claude/rules/backend-add-cache-in-service.md. The test registry_containsEveryCacheName_whenBuilt checks the registry vortibhai/src/test/java/com/admission/vortibhai/config/CacheTypeRegistryTest.java:27.

    You change a cached DTO or entity shape high

    Old JSON in Redis no longer matches the new class. Reads then fail with Cache GET failed until the TTL ends. Bump CacheConstants.NAMESPACE (now vb:v12:, CacheConstants.java:5) so the app uses new keys and ignores the old ones. Note: 4 caches store entities directly (University, Department, DepartmentSummary, DropDownDepartment, CacheTypeRegistry.java:56,66,67,71). A change to these entity classes counts too.

    Self-call skips the cache high

    Spring caches through a proxy. this.getX() inside the same class does not pass through the proxy. The project solves this for FAQ: FaqServiceImpl calls the cached FaqPageQueryService.fetchQuestionPage on a separate bean (FaqServiceImpl.java:104), then adds the per-user "liked" flag after the cache. Use the same split when you need a cached base plus per-user data.

    Forgot an eviction on a new write path high

    Nothing fails. Users just see old data for up to 1 TTL (up to 60 minutes for dept-summary, dept-facets, categories). When you add a write method, copy the @Caching block from the closest sibling, for example DepartmentServiceImpl.java:816-830, and check every cache that shows the changed data.

    Never cache user-specific data in a shared key high

    The key decides who shares an entry. If a result depends on the current user (likes, role, anonymous id) and the key does not include it, user A sees user B's data. The FAQ split above exists for this reason.

    Optional returns and unless medium

    Spring unwraps Optional. Register the inner type and write unless = "#result == null", as getSummary does (DepartmentSummaryServiceImpl.java:118-121). #result.isEmpty() does not work, because SpEL sees the unwrapped value.

    Key format must match between read and evict medium

    dept-group uses departmentId:universityId. dept-reviews uses universityId:departmentId:.... The order differs between caches. A wrong order in an exact-key evict deletes nothing and logs nothing.

    Null in a key expression medium

    Keys use (#query ?: '') and (#approved ?: 'all') to turn null into a fixed string (UniversityServiceImpl.java:161). Without it, the key contains the text null, which can collide with a real value. search skips the cache for a blank query with condition (SearchServiceImpl.java:50).

    Do not remove delegate.afterPropertiesSet() medium

    It looks unused. Without it, the per-cache TTL and serializers are ignored (CacheConfig.java:63-66).

    Default TTL is written in 2 places low

    CacheConfig.DEFAULT_TTL (CacheConfig.java:31) and the admin list fallback (CacheAdminServiceImpl.java:64) both say 5 minutes. If you change one, change the other. Also, formatTtl shows minutes only, so a TTL below 60 seconds shows as 0m (CacheAdminServiceImpl.java:130-138).

    Environment differences low

    Local runs expect Redis at localhost:6379 (application.properties:106-107). If it is not running, the app still works but every cached call waits up to 250 ms and logs WARN lines. Start it with docker compose up -d redis. TTLs can differ per environment through cache.ttl.<name>=PT10M.

    X-Cache shows only the first cached call low

    If an endpoint calls 2 cached methods, the header shows the result of the first lookup only (CacheStatusHolder.java:12-16). A HIT header does not prove that the whole request skipped MongoDB. Check X-Db-Queries too.
